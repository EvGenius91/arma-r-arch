# Общие концепции

## GameBackendManager

Связующее между игровым сервером и бекендом: RPC/запросы к бекенду и приём сигналов с бекенда.

Пример: `TSM_BankingGameBackendManager` имеет методы взаимодействия с бекендом и слушает события от бекенда.

## Local EventBus — единая точка диспетчеризации

На игровом сервере события раздаются через **локальный EventBus**.

### Правило

> **Все события с бекенда обязательно публикуются в Local EventBus.** Дальше идёт только диспетчеризация по подпискам — даже если слушатель один.

Мост (`GameBackendManager` и доменные аналоги) **не** вызывает меню, CSM или другие сервисы напрямую. Он только:

```text
бекенд → GameBackendManager → EventBus.publish(...) → подписчики
```

Пример: пришло событие с бекенда об изменении наличных → `TSM_BankingGameBackendManager` публикует `CashChanged` (или аналог) в EventBus → подписываются компонент меню магазина и компонент оповещений; каждый сам решает, что делать. Сам `GameBackendManager` не должен знать про меню и не должен менять сумму в UI.

То же для `CharacterStateChanged`: мост публикует в EventBus; CharacterStateManager (и при необходимости UI) подписаны на это событие.

### Источники событий в EventBus

| Источник | Пример | Кто публикует |
|----------|--------|----------------|
| Сигнал с бекенда | `CashChanged`, `CharacterStateChanged` | GameBackendManager → EventBus |
| Локальный apply в мире | предмет удалён, деньги зачислены после CommandBus | профильный сервис → EventBus |

### Чего EventBus не делает

- **не отправляет** события на бекенд (игра → бекенд: RPC — character ops через CSM / `applyOperations`, предметы через EntityManager);
- **не меняет** мир сам (мутации с бекенда — [[Architecture/BackendGameMutation.md|CommandBus]]);
- **не обязан** иметь подписчиков: отсутствие слушателей — нормальная ситуация.

### Анти-паттерн

Прямая раздача с моста на конкретные компоненты/сервисы в обход EventBus («иногда в шину, иногда напрямую») — **запрещена**. Исключение только для отладки, не для продакшен-архитектуры.
